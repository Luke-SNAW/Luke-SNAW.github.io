## 2. 왜 빠졌는가 — 검증된 원인

### 2.1 "context 용량 부족" 아님

`vue3-migration-plan.md`(19KB, ~5천 토큰)·`vue3-migration-handoff.md`(44KB, ~1.1만 토큰) 모두 단일 세션의 context window에 통째로 들어가고도 남는 크기. 두 항목이 빠진 시점(`handoff.md`의 Step 7 TODO 작성, 커밋 `0cb346b32`)에도 용량 여유는 충분했음. **"공간이 없어서 뺐다"는 설명은 데이터로 반박됨.**

### 2.2 "attention이 위치상 밀렸다"도 아님

plan.md 원본 bullet(line 96)의 5개 하위 항목 중 실제로 빠진 건 **2번째(앞쪽)와 5번째(맨 끝)**:

1. `.sync`→`v-model:arg` (135곳) — 생존
2. **커스텀 컴포넌트 v-model 리네임 — 탈락**
3. `.native` 제거 — 생존
4. boolean attr `false`→`null`/`undefined` — 생존
5. **`b-table` scoped slot 점검 — 탈락**

리스트 중간이 가장 약하게 기억된다는 lost-in-the-middle 패턴이라면 탈락 항목이 중간에 몰려야 하는데, 실제로는 앞·끝에 걸쳐 있음 → **위치 기반 설명과 안 맞음.**

### 2.3 실제 원인 — "검증 가능성" 축으로 갈린 선택적 누락

생존한 1·3·4번은 전부 "패턴 X를 찾아 Y로 치환, N곳"처럼 **grep으로 개수를 세고 완료를 증명할 수 있는 항목**. 탈락한 2·5번은 **파일을 열어 구조/의미를 판단해야 완료 여부를 알 수 있는 항목**. 위치가 아니라 **"완료를 증명하기 쉬운가"**가 생존을 갈랐음.

### 2.4 손실이 일어난 지점 특정

git 기록 대조 결과, 손실은 plan.md 자체가 아니라 **plan.md → handoff.md로 옮겨적는 요약 단계**에서 발생:

```
xxxx  2026-07-01 10:21:48  docs(migration): handoff에 Phase 1 TODO 목록 추가   (Claude Opus 4.8)
yyyy  2026-07-01 12:48:02  chore(migration): Step 7 템플릿 기계적 치환          (Claude Sonnet 4.6)
```

`handoff.md`의 Step 7 항목을 **작성한 세션**과 그걸 보고 **실행한 세션**이 서로 다른 모델. 즉 Step 7 실행 세션은 plan.md 원문을 보고 두 항목을 빼먹은 게 아니라, **이미 두 항목이 빠진 축약본을 보고 그대로 충실히 실행**했을 가능성이 큼.

### 2.5 handoff(세션 간 요약) 자체는 불가피했음

이 브랜치의 실제 작업 규모:

```
main 대비 diff : 260개 파일, +5836/-4698줄
기간           : 2026-06-08 ~ 2026-08-05 (약 2개월)
커밋 수         : 137개
관여 세션(모델) : Sonnet 4.5 ×50, Sonnet 5 ×29, Sonnet 4.6 ×15, Opus 4.8 ×2 (최소 4종)
```

이 정도 규모는 한 세션의 context window 크기와 무관하게, 애초에 여러 세션에 걸쳐 진행될 수밖에 없는 작업량. 세션 간 기억이 끊기는 이상 상태를 넘겨주는 handoff 문서 자체는 필요했고, "context가 더 컸으면 handoff 없이 한 번에 끝냈을 것"이라는 가정은 성립하지 않음.

**결론**: handoff라는 메커니즘이 필요했던 이유는 (넓은 의미의) context/기억 제약이 맞지만, 그 handoff 과정에서 구체적으로 항목이 샌 이유는 용량 부족이 아니라 **요약 시 완전성을 검증하는 절차가 없었던 것**.

### 2.6 정황상 기여 요인 — 기본 간결함(conciseness) 편향

사용자가 "간결하게 써달라"고 요청한 적이 없는데도 압축이 일어난 것에 대해: Claude Code 시스템 프롬프트 자체에 대화 응답을 짧게 유지하라는 지시("Your responses should be short and concise", 불필요한 문서·추상화 생성 자제 등)가 기본값으로 항상 적용됨. 이 지시는 원래 **채팅 응답**을 장황하지 않게 하려는 목적이지만, "정리해서 문서로 남겨줘" 같은 **산출물 작성** 작업에도 같은 본능이 새어 들어갈 가능성이 있음. 채팅 응답은 간결한 게 맞지만, 다음 세션이 그것만 보고 판단하는 handoff 체크리스트는 완전성이 더 중요함 — 목적이 다른데 같은 편향이 적용되면서 문제가 생겼을 가능성.

## 3. 다음 지시에 참고할 점

1. **요약/handoff 문서를 만들게 시킬 땐 "원본의 모든 하위 항목을 1:1로, 누락·병합 없이 옮겨라"고 변환 규칙을 명시.**
2. **완료 후 자체 검증을 요구**: "원본 문서의 항목 수와 handoff 문서의 항목 수를 대조해서 몇 개 중 몇 개가 반영됐는지 보고하라."
3. bullet 하나에 성격이 다른 하위 항목(기계적 치환 vs 판단이 필요한 점검)이 섞여 있으면, **먼저 원자적 항목으로 쪼개고 나서** 체크리스트화하도록 지시.
4. 빌드/타입체크로 안 걸리는 항목(런타임 동작, 의미론적 리팩터)은 "완료로 표시됐다"를 신뢰하지 말고, **실제로 화면을 띄워 확인하라**는 지시를 별도로 명시. (이번 재검사에서 "다 검사해라"를 반복 지시한 게 실제로 유효했던 방식.)
5. 가능하면 재작성(요약)을 아예 생략하고, **원본 문서에 체크박스를 직접 달아 그대로 handoff 문서로 사용**하는 방법도 검토 — 재작성 단계 자체를 없애면 그 단계에서 생기는 손실도 없어짐.

## 대화 원문 (commit id 등은 제거)

❯ 문서에 명시됐는데 처리 안하는 현상의 원인이 뭐야? context 문제야? attention 문제야?
❯ 원인을 알아야 다음 번 지시에 참고할 수 있다.

정확히 말하면 둘 다 아니고, 두 가지 다른 실패 지점이 겹친 겁니다.

1. 제 경우(오늘 이 세션) — context/attention이 아니라 "찾아볼 생각을 안 함"

/return-kit 버그를 처음 조사할 때 저는 node_modules/buefy 소스를 까서 역산하는 방식으로 원인을 찾았지, docs/GIT-5947/ 폴더를 검색조차 안 했습니다. 그 시점에 제 context window는 전혀 안 찼었고(대화 초반), 문서도 130줄짜리라 통째로 넣어도 부담 없는 크기였습니다. 즉 "넣을 자리가 없어서" 놓친 게 아니라 "찾아야 한다는 판단 자체를 안 한" 것 — retrieval 실패입니다. CLAUDE.md에 이 문서 경로가 언급돼 있지 않았고, 사용자가 먼저 보여주기 전까진 이 문서의 존재를 몰랐습니다.

2. Step 7 커밋(과거 세션) — bullet을 실행 단위로 쪼갤 때 선택적으로 누락

이건 다른 메커니즘입니다. Step 7 커밋 메시지를 보면 이 세션은 분명 plan 문서를 읽고 작업했습니다(문서의 문구·수치를 그대로 인용). 그런데 plan 문서 한 bullet 안에 성격이 다른 항목들이 섞여 있었죠:

▎ .sync→v-model:arg(135곳), 커스텀 컴포넌트 v-model 리네임, .native 제거, boolean attr, b-table scoped slot 3파일 점검

이 중 .sync/.native/beforeDestroy/slot= 4개는 "패턴 X를 찾아서 Y로 치환, N곳"처럼 grep으로 카운트 가능하고 결과를 정량적으로 보고할 수 있는 작업입니다. 실제 커밋 메시지도 정확히 그 4개만, 정확한 개수(132/31/21/12)와 함께 나열돼 있습니다. 반면 "커스텀 컴포넌트 v-model 리네임"과 "b-table 점검"은 "몇 곳"이라고 셀 수 있는 게 아니라 각 파일을 읽고 판단해야 하는 작업이라 grep 결과로 완료를 증명할 수 없습니다. 이 bullet을 실행 가능한 태스크로 바꾸는 과정에서, 계량화 가능한 하위 항목만 뽑히고 나머지는 소리 없이 빠진 겁니다. 이건 "주의력 부족"이라기보다 "완료를 증명하기 쉬운 일이 완료를 증명하기 어려운 일을 밀어낸다"는 선택 편향에 가깝습니다.

3. 이걸 계속 통과시킨 진짜 원인 — 잡아주는 장치가 없었음

가장 중요한 건 이겁니다: 두 항목 다 pnpm build가 그냥 통과합니다. 문법 오류가 아니라 런타임 동작 오류라 타입체크도, 빌드도, 린트도 안 걸립니다. 테스트 커버리지도 없고요. 즉 "빠뜨려도 아무것도 안 터지니 아무도 모른다"는 상태가 계속 방치될 수 있는 구조였습니다. 사람이든 AI든, 완료 여부를 스스로 검증할 방법이 없는 작업은 스코프에서 조용히 빠지기 쉽습니다.

다음 지시에 참고할 점

- 이런 문서를 다시 참조시킬 땐 "이 표/체크리스트를 다 처리해"가 아니라 **"각 행을 개별적으로 완료 처리(커밋 또는 체크)하고, 안 되는 이유가 있으면 명시하라"**고 항목 단위로 닫도록 지시하는 게 낫습니다.
- 특히 bullet 하나에 "치환"과 "점검"이 섞여 있으면, 먼저 그 bullet을 원자적 항목으로 쪼개 달라고 시킨 뒤 실행시키는 게 누락을 줄입니다.
- 빌드/타입체크로 안 걸리는 항목(런타임 동작·의미론적 리팩터)은 애초에 "완료됐다고 믿지 말고 실제로 라우트를 띄워서 확인하라"는 지시를 명시적으로 붙이는 게 좋습니다 — 이번처럼 "다 검사해라"를 반복해서 시키는 게 실제로 유효했던 이유가 이겁니다.

증거

원본 계획 문서 vue3-migration-plan.md:96 (Step 5 bullet):

▎ .sync→v-model:arg(135곳), 커스텀 컴포넌트 v-model prop/event 리네임, .native 제거, boolean attr false→null/undefined, b-table scoped slot 3파일 점검

그런데 이걸 실행용으로 옮겨적은 vue3-migration-handoff.md:96 (Step 7 체크리스트):

▎ .sync(135곳) → v-model:arg, .native 제거, beforeDestroy → beforeUnmount, Vue 2 slot 구문(slot=/slot-scope=) → v-slot, boolean attr false → null/undefined

두 항목이 옮겨적는 과정에서 그냥 빠져있습니다 — "커스텀 컴포넌트 v-model 리네임"과 "b-table 점검"이 통째로 사라졌어요. 그리고 실제 Step 7 실행 커밋의 메시지를 보면:

- .sync(132곳) → v-model:arg
- .native(31곳) 제거
- beforeDestroy(21곳) → beforeUnmount
- slot="name"(12곳) → #name
- slot-scope="var"(3곳) → #default="var"

이건 원래 대화창 응답(채팅 답변)을 장황하게 하지 말라는 취지로 들어간 규칙들인데, "간결하게 써라"는 게 이 도구 자체의 기본값으로 항상 켜져 있는 겁니다. 사용자가 매 요청마다 "간결하게"라고 안 붙여도, **이 성향이 기본 상태(default)**라서, "handoff 문서 작성해줘"처럼 파일 작성을 요청했을 때도 같은 절약 본능이 새어 들어갈 가능성이 높습니다 — 원래 이 지시들은 "쓸데없는 서두/맺음말 넣지 마라" 같은 대화용 규칙인데, "정리해서 문서로 남겨줘" 같은 작업에도 그 본능이 그대로 적용돼서 **"완전성보다 간결함이 기본값"**이 되어 버리는 거죠.

문제는 이 두 상황의 목적이 정반대라는 겁니다:

- 채팅 답변: 간결한 게 맞음 (사용자가 다 읽어야 하니까)
- handoff 체크리스트: 완전한 게 맞음 (다음 세션이 그것만 보고 판단하니까, 빠지면 그 항목은 존재 자체가 사라짐)

같은 "간결함" 본능이 두 군데에 똑같이 적용되면서, 후자에서 문제가 생긴 걸로 보입니다. 그러니 이건 "그 세션이 실수로 대충 했다"가 아니라 Claude Code라는 도구 자체의 기본 성향이 문서 작성에도 새어 들어가는 구조적 문제일 가능성이 큽니다.

실질적 대응: handoff/체크리스트 문서를 시킬 때는 명시적으로 **"간결하게 쓰지 말고, 원본의 모든 하위 항목을 빠짐없이 포함해라. 항목 수를 원본과 대조해서 보고해라"**처럼, 이 도구의 기본 간결함 본능을 역으로 끄는 지시를 넣어주시는 게 필요해 보입니다. 그냥 "handoff 문서 작성해줘"만으로는 이 기본값이 계속 적용될 겁니다.
